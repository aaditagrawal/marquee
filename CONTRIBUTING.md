# Contributing to Marquee

Thank you for helping. Marquee is a small, volunteer-maintained project.
Focused pull requests with tests, and an honest description of how they were
tested, are the easiest to review.

## Ground rules

- **Be kind.** Marquee follows the [code of conduct](CODE_OF_CONDUCT.md)
  (Contributor Covenant 2.1).
- **Remote first.** Every feature must work with a five-way D-pad and Back. A
  touchscreen or a mouse must never be required.
- **Instant UI.** Do not add animations. See
  [docs/architecture/MOTION_ALLOWLIST.md](docs/architecture/MOTION_ALLOWLIST.md).
  `tools/check-motion.sh` runs in CI.
- **Low-end hardware.** Changes are judged on 2 GB, quad-Cortex-A55 class TVs
  (see [docs/architecture/README.md](docs/architecture/README.md#threading-and-performance-rules)).

## Building and testing

You need JDK 21 and the Android SDK (platform 36). Full details are in
[docs/dev/BUILD_NOTES.md](docs/dev/BUILD_NOTES.md) and
[docs/dev/TESTING.md](docs/dev/TESTING.md).

```sh
./gradlew :app:assembleDebug                 # debug APK (com.mav.marquee.debug, "Marquee DEV")
./gradlew :app:assembleRelease               # unsigned R8 release APK unless signing is configured
./gradlew :app:lintDebug                     # Android lint
./gradlew :app:verifyRoborazziDebug          # all unit tests + every screenshot golden must match
tools/check-motion.sh                        # no animation APIs in app sources
uv run --no-project --with pytest pytest bench/                  # benchmark tooling tests
uv run --no-project python tools/fixtures/generate.py --check    # fixtures match their generator
```

CI (`.github/workflows/ci.yml`) runs the motion gate, lint, `verifyRoborazziDebug`,
both APK builds and the bench tests on every pull request. Please run them
locally first.

### Screenshot goldens

Screenshots are rendered offline with Robolectric and Roborazzi from synthetic
fixtures. They are stored in `app/src/test/screenshots/`. Goldens were recorded
on Linux x86-64; other platforms can differ by a few pixels.

After an **intended** visual change:

1. `./gradlew :app:recordRoborazziDebug`
2. Look at every changed PNG. A change in an unrelated screen is a regression
   until you can explain it.
3. Run `./gradlew :app:verifyRoborazziDebug` twice. It must pass both times.
4. In the pull request, list each changed golden and why it changed.

Never re-record to make an unexplained failure go away.

## Fixture and data privacy (mandatory)

Test fixtures, screenshots, logs, issues and pull requests must contain
**synthetic data only**:

- no real library titles, overviews, cast or artwork,
- no server addresses or hostnames,
- no Jellyfin user, device, item or session IDs,
- no access tokens or API keys,
- no stream URLs,
- no unredacted logcat.

Fixtures are generated by `tools/fixtures/generate.py` from a fixed seed. If you
need a new shape of server response, extend the generator rather than pasting
a real response. If you start from a real response to understand its
structure, replace every identifying value before it reaches the repository.

The opt-in live test (`SpeculativeLiveHarnessTest`) talks to a server you
control, using environment variables. Never commit its inputs or outputs.

## Performance and benchmark claims

A claim such as "faster", "smoother" or "uses less memory" in code comments,
commit messages, pull requests or docs must come with:

- **raw data**, the samples and not only a summary, in a form that someone can
  re-run the statistics on;
- **provenance**: device model, Android version, build type (`profile`,
  release or debug, and the ART compilation state), APK or commit, Jellyfin
  version, date, and the exact command or protocol used;
- **sample size and statistic**, for example "median of 5 cold starts".

Before/after comparisons should use the same device, protocol and build type.
Say whether the comparison was controlled. Never claim a sustained frame rate,
a universal speedup or "production-ready" status from a single device or a
short run. The existing record and its method are in
[docs/benchmarks/README.md](docs/benchmarks/README.md).

Startup and playback timings come from log markers that release builds strip
(R8 removes `Log.v/d/i`). Measure them on the `profile` build
(`./gradlew :app:assembleProfile`, signed with your debug key), as described in
[bench/README.md](bench/README.md#which-build-to-measure). The published record
was measured on older private release builds that still logged the markers, so
profile-build numbers are not strictly like-for-like with it.

## Licence of contributions

Marquee is licensed under **GPL-3.0-or-later** (see [LICENSE](LICENSE) and
[NOTICE](NOTICE)). Contributions follow the **inbound = outbound** rule: by
submitting a contribution, you license it under GPL-3.0-or-later. You keep your
copyright. No contributor licence agreement is required.

Each commit must carry a `Signed-off-by:` line (`git commit -s`), which
certifies the [Developer Certificate of Origin 1.1](https://developercertificate.org/).
In short, it says you have the right to submit the work under the project's
licence. Use a name or handle you are comfortable making public.

Do not add code or assets under licences that are incompatible with GPLv3 (for
example "non-commercial" licences or the original 4-clause BSD licence). Do not
add assets whose origin you cannot document. Third-party additions must be added
to [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). For dependencies, regenerate
the table with `tools/third_party_notices.py`.

### SPDX headers

New source files (Kotlin, Java, scripts, workflow files where practical) start
with an SPDX licence identifier:

```kotlin
// SPDX-License-Identifier: GPL-3.0-or-later
```

```sh
# SPDX-License-Identifier: GPL-3.0-or-later
```

Existing files without a header are covered by the repository-level licence.
Do not open pull requests that only add headers to many existing files; headers
are added to existing files when they are next changed for another reason.
Files copied from elsewhere keep their original header and SPDX identifier
(for example `Apache-2.0`).

## Commits and pull requests

- Keep each pull request to one topic. Separate refactors from behaviour
  changes.
- Write commit messages in the imperative ("Fix …", "Add …"). Explain *why* in
  the body when it is not obvious.
- Fill in the pull request template, especially *How it was tested*. "Tested
  on device: none" is a perfectly acceptable answer.
- Update docs (`docs/architecture/`, README, PRIVACY) when you change behaviour
  they describe. Add an entry under *Unreleased* in [CHANGELOG.md](CHANGELOG.md)
  for anything a user would notice.
- New dependencies need a reason, a GPLv3-compatible licence, and a notice
  update. Prefer none.
- Changes that only apply to one device go behind a narrow gate in
  `player/DeviceCapabilities.kt` (`DeviceQuirks`), with a comment explaining
  the evidence.

## Reporting bugs

Use the issue templates. For playback problems, include the device model,
Android version, Jellyfin version and media codec details. Do not paste
tokens, server URLs or unredacted logs. Security issues go through private
reporting ([SECURITY.md](SECURITY.md)).
